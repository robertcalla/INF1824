\begin{abstract}
This work reports on the progress of an Artificial Intelligence system aimed
at automatically identifying and correcting \emph{level design} bottlenecks
in physics-based 2D stages. The development environment is built on the
Godot~4.7 engine, targeting multiplayer mechanics. Unlike traditional
navigation (\emph{pathfinding}) approaches, the goal is to train an agent
capable of analyzing the topology of a map, identifying congestion zones
that hinder gameplay flow, and applying content-generation techniques to
suggest scenario adaptations. We propose an architecture that combines a
structured 2D-grid representation of the environment, spatial feature
extraction via a Convolutional Neural Network (CNN), and a Deep
Reinforcement Learning (DRL) agent inspired by \emph{Curiosity-Driven
Exploration} and \emph{Procedural Content Generation via Reinforcement
Learning} (PCGRL). We formalize the problem as a Markov Decision Process,
specify a concrete network architecture (convolutional feature extractor,
actor-critic heads, and Intrinsic Curiosity Module) together with a
reference set of PPO hyperparameters, describe the current implementation
status, and lay out an evaluation methodology -- with explicitly defined
metrics, baselines, and an experimental protocol -- for the next
development cycles. As of this writing, agent training has not yet been
executed; no performance results are reported, and every number in
Section~\ref{sec:arquitetura} is a proposed design choice to be tuned
empirically, not an outcome of a completed experiment. We also discuss the
main methodological risks, most notably \emph{reward hacking}, and outline
a roadmap of future work.
\end{abstract}

\section{Introduction}

\emph{Level design} is one of the pillars of the player experience: the way
corridors, rooms, obstacles, and alternative routes are arranged directly
determines the pacing, the perceived difficulty, and the fluidity with
which a player progresses through a stage. However, manually identifying
friction points that hurt this fluidity -- so-called \emph{bottlenecks} --
is a costly, subjective process that depends on extensive human
\emph{playtesting} sessions. In productions with short iteration cycles, or
in procedurally generated stages, this cost becomes even more critical,
since every new version of a level would require a new round of manual
testing.

This work reports on the progress of research and development of an
Artificial Intelligence application for identifying and correcting these
bottlenecks. The development environment is being built on the
Godot~4.7~\cite{godotengine} engine, focusing on physics-based 2D stages
and multiplayer mechanics -- a domain in which navigation bottlenecks
affect not just a single player, but the dynamics of multiple agents
competing for the same space.

\subsection{Motivation}

The central motivation of this project is that automated, AI-based
playtesting tools can reduce the iteration cost of the level-design
process, allowing designers to receive quantitative feedback about a
level's structural quality before ever exposing it to human testers.
Unlike static graph-analysis heuristics (for example, centrality measures
over the navigability graph), a reinforcement-learning agent can capture
dynamic gameplay effects -- such as congestion caused by multiple players
competing for the same corridor -- that are not trivial to express as a
fixed rule.

\subsection{Problem Statement}

The goal of the project is to go beyond simple navigation
(\emph{pathfinding}). The aim is to train a machine-learning agent capable
of:
\begin{enumerate}
  \item analyzing the topology of the map from a structured representation
    that is independent of graphical rendering;
  \item identifying congestion zones that hurt gameplay flow, i.e., regions
    of the map where the traversal flow between points of interest is
    abnormally low; and
  \item applying content-generation techniques to suggest scenario
    adaptations that alleviate these bottlenecks, closing the loop between
    diagnosis and correction.
\end{enumerate}
In other words, the agent should not merely traverse the level, but learn
to point out -- and eventually correct -- structural design flaws.

\subsection{Contributions}

The contributions of this progress report are:
\begin{itemize}
  \item an environment-representation architecture that is independent of
    graphical rendering, based on 2D matrices extracted directly from
    Godot's \texttt{TileMap} and \texttt{NavigationServer2D};
  \item a formalization of the problem as a Markov Decision Process (MDP),
    with a state space, an action space, and a proposed hybrid
    (intrinsic~+~extrinsic) reward function;
  \item a concrete, fully specified network architecture -- convolutional
    feature extractor, actor-critic heads, and Intrinsic Curiosity Module
    -- together with a reference set of PPO hyperparameters, proposed as a
    starting point for the upcoming implementation;
  \item a planned evaluation methodology, with explicitly defined metrics
    (including their formulas), baselines, and an experimental protocol,
    still to be executed in the next project cycles; and
  \item an initial discussion of methodological limitations and risks,
    most notably the risk of \emph{reward hacking}.
\end{itemize}

\section{Related Work}
\label{sec:relacionados}

The use of reinforcement learning for game-content generation and
evaluation has been consolidating as an alternative to traditional
rule-based or search-based procedural content generation
(PCG)~\cite{shaker2016procedural}. This section reviews three lines of work
that underpin the proposed architecture: procedural content generation via
reinforcement learning, automated playtesting with human-like agents, and
curiosity-driven exploration.

\subsection{Procedural Content Generation via Reinforcement Learning}

Khalifa et~al.~\cite{khalifa2020pcgrl} propose PCGRL (\emph{Procedural
Content Generation via Reinforcement Learning}), in which level generation
is formulated as a sequential decision-making problem: an agent edits the
map tile by tile and receives rewards according to quality metrics of the
resulting level (for example, connectivity, number of reachable enemies, or
shortest-path length). Unlike generative models trained through supervised
learning on corpora of existing levels, PCGRL does not depend on large
annotated datasets, but on a well-defined reward function over the space of
levels -- a central characteristic that we aim to reuse in this project.
This formulation directly inspires the state representation and action
space discussed in Section~\ref{sec:arquitetura} of this work.

\subsection{Automated Playtesting with Human-Like Agents}

On the automated-playtesting front, De~Woillemont
et~al.~\cite{dewoillemont2022automated} use reinforcement learning to
generate agents with human-like play styles, enabling a game to be tested
under varied behavior profiles without relying on human testers for every
iteration. This line of work starts from the premise that a purely optimal
agent (for example, one that always finds the shortest path) is not
representative of real player behavior, since players explore, hesitate,
and make mistakes. Sestini et~al.~\cite{sestini2022automated} extend this
line by proposing curiosity-conditioned proximal trajectories for automated
\emph{gameplay} validation, combining curiosity-guided exploration with
trust-region policy-optimization methods to detect rare or problematic game
states (for example, \emph{softlock} situations or bug exploitation).

\subsection{Curiosity-Driven Exploration}

The curiosity-guided exploration component used in this project follows
the formulation of the Intrinsic Curiosity Module (ICM) proposed by Pathak
et~al.~\cite{pathak2017curiosity}, in which a predictive model learns to
anticipate the latent representation of the next state from the current
state and action; the prediction error is used as an intrinsic reward,
encouraging the agent to visit regions of the environment whose dynamics
have not yet been well modeled. This mechanism is particularly well suited
to our scenario, since level-design bottlenecks tend to correspond to
regions that are seldom visited by naive navigation policies -- exactly the
regions that a curiosity signal tends to prioritize.

\subsection{Positioning of This Work}

Table~\ref{tab:relacionados} summarizes how the present work relates to the
three works discussed above. This project sits at the intersection of
these lines: like PCGRL, it uses a matrix-based level representation as the
state of a Markov decision process; and, like the automated-playtesting
works, it incorporates curiosity-guided exploration -- not to generate
player styles, but so that the agent itself discovers and flags regions of
the map with low traversal flow, treating bottleneck detection as the
central objective of the reward, rather than merely a by-product of
exploration.

\section{Problem Formalization}
\label{sec:formalizacao}

\subsection{Level Design Bottlenecks}

We informally define a bottleneck as a region of the level whose traversal
flow -- the number of times agents pass through that region during a
gameplay episode, normalized by the total episode duration -- is
significantly lower than expected for a region with equivalent
connectivity in the navigation graph. This definition captures both
``structural'' bottlenecks (a narrow corridor that physically limits the
simultaneous passage of multiple players) and ``behavioral'' bottlenecks (a
fork that players tend to avoid because it subjectively seems less
advantageous).

\subsection{Markov Decision Process}

We model the problem as a Markov Decision Process (MDP) $\langle
\mathcal{S}, \mathcal{A}, P, R, \gamma \rangle$, in which:

\begin{itemize}
  \item $\mathcal{S}$ is the state space, defined by the 2D matrix $G \in
    \{0,1\}^{H \times W}$ that represents the level
    (Section~\ref{sec:representacao}), possibly augmented with additional
    channels encoding the agent's position and points of interest
    (entrance, exit, items);
  \item $\mathcal{A}$ is the action space, detailed in
    Section~\ref{sec:acao};
  \item $P(s_{t+1} \mid s_t, a_t)$ is the transition dynamics, determined
    by Godot's physics and navigation engine;
  \item $R(s_t, a_t, s_{t+1})$ is the reward function, detailed in
    Section~\ref{sec:recompensa}; and
  \item $\gamma \in [0,1)$ is the discount factor.
\end{itemize}

The training objective is to find a policy $\pi_\theta(a_t \mid s_t)$,
parameterized by a neural network with parameters $\theta$, that maximizes
the expected return
\begin{equation}
  J(\theta) = \mathbb{E}_{\pi_\theta}\!\left[ \sum_{t=0}^{T} \gamma^t
  R(s_t, a_t, s_{t+1}) \right].
  \label{eq:objective}
\end{equation}

\subsection{State Space}
\label{sec:representacao}

The state observed by the agent at each instant $t$ is the matrix $G_t$
described in Section~\ref{sec:representacao-ambiente}, processed by a
convolutional feature extractor $\phi(\cdot)$ (Section~\ref{sec:cnn}) that
produces a latent feature vector $z_t = \phi(G_t) \in \mathbb{R}^d$. This
latent vector is the input to both the policy network and the curiosity
module.

\subsection{Action Space}
\label{sec:acao}

We propose a hybrid action space, reflecting the two-phase nature of the
problem (navigation and, later, content editing):
\begin{itemize}
  \item \textbf{Navigation actions}: a discrete displacement vector
    $a^{\text{nav}} \in \{\text{north}, \text{south}, \text{east},
    \text{west}, \text{stay}\}$, matching the granularity of the tile
    matrix;
  \item \textbf{Flagging/editing actions} (later project phase):
    $a^{\text{edit}} \in \{\text{none}, \text{flag bottleneck}, \text{remove
    blockage}, \text{add blockage}\}$, applied to the matrix cell
    corresponding to the agent's current position.
\end{itemize}
In the current project phase, only $a^{\text{nav}}$ is in use; the editing
space will be incorporated progressively, as discussed in
Section~\ref{sec:futuro}.

\subsection{Reward Function}
\label{sec:recompensa}

We propose a hybrid reward function, combining an extrinsic term
$r^{\text{ext}}_t$, responsible for penalizing bottlenecks, and an
intrinsic term $r^{\text{int}}_t$, responsible for guiding exploration:
\begin{equation}
  R(s_t, a_t, s_{t+1}) = r^{\text{ext}}_t + \beta \, r^{\text{int}}_t,
  \label{eq:reward}
\end{equation}
where $\beta$ is a coefficient balancing the two terms.

The extrinsic term penalizes cells with low traversal flow. Let $\tau(v)$
be the accumulated traversal flow of cell $v$ over a window of $N$
episodes, and $\theta_\tau$ a threshold below which a cell is considered a
bottleneck. We define
\begin{equation}
  r^{\text{ext}}_t = -\sum_{v \,\in\, \mathcal{V}(s_t)} w(v) \cdot
    \mathbb{1}\!\left[\tau(v) < \theta_\tau\right],
  \label{eq:reward-ext}
\end{equation}
where $\mathcal{V}(s_t)$ is the immediate neighborhood of the agent's
position in $s_t$ and $w(v)$ is a weight proportional to the centrality of
cell $v$ in the navigation graph -- so that bottlenecks on central routes
are penalized more strongly than bottlenecks in marginal regions of the
map.

The intrinsic term follows the ICM formulation~\cite{pathak2017curiosity}:
a predictive model $f_\psi$ estimates the latent representation of the next
state, $\hat{z}_{t+1} = f_\psi(z_t, a_t)$, and the prediction error is used
as a reward,
\begin{equation}
  r^{\text{int}}_t = \frac{\eta}{2} \, \lVert \hat{z}_{t+1} - z_{t+1}
    \rVert_2^2,
  \label{eq:reward-int}
\end{equation}
where $\eta$ is a scaling constant. The intuition is that regions of the
level whose dynamics are poorly modeled by the agent -- typically
seldom-visited regions, such as bottlenecks -- produce a larger prediction
error and therefore a larger intrinsic reward, complementing the extrinsic
signal of Equation~\eqref{eq:reward-ext} during the early stages of
training, when the estimates of $\tau(v)$ are still noisy.

which the center cell of the middle column is the only passage point
between the left and right halves of the level.

  \label{fig:exemplo-grid}

In this example, a naive navigation agent (for example, one trained only
with a sparse reward for reaching the exit) tends to cross cell
\textbf{B} with the same frequency as any other cell along the path, since
it is, by definition, the only possible route -- there is therefore no
signal that this cell is structurally different from the others simply by
observing visitation frequency. This is why Equation~\eqref{eq:reward-ext}
weights the flow $\tau(v)$ by the centrality $w(v)$ of the cell in the
navigation graph: cell \textbf{B} has a much higher betweenness centrality
than the other cells in the corridor, since every path between the two
halves of the level necessarily passes through it. A value of $\tau(v)$
comparable to that of the other free cells, combined with a high $w(v)$, is
what flags \textbf{B} as a relevant structural bottleneck, rather than just
another passage cell. In corridors with multiple alternative paths, on the
other hand, the centrality of each individual cell tends to be lower, and a
bottleneck only emerges when the observed flow $\tau(v)$ falls
significantly below what is expected for cells of comparable centrality --
it is this combination of static topology ($w(v)$) and observed dynamic
behavior ($\tau(v)$) that we aim to capture with the proposed reward
function, and that a purely structural heuristic (considering only $w(v)$)
could not distinguish on its own.

\subsection{Development Environment}

The development environment is being built on the
Godot~4.7~\cite{godotengine} engine, chosen for its native support for
deterministic 2D physics, its navigation system
(\texttt{NavigationServer2D}), and the ease of introspecting scene data via
GDScript, which allows the structured level representation to be extracted
without any image-processing step.

\subsection{Environment Representation}
\label{sec:representacao-ambiente}

After evaluating the best input strategy for the AI, we discarded the use
of direct camera images (pixel rendering): processing textures and
lighting would add unnecessary computational cost to the neural network,
without contributing information relevant to the bottleneck-identification
task, which is fundamentally structural, not visual.

The established solution is the structured extraction of the map as a 2D
matrix (\emph{grid}). Using Godot~4.7's built-in features, the
\texttt{TileMap} and the \texttt{NavigationServer2D} meshes are mapped to
produce a two-dimensional array whose values represent terrain states:
\begin{itemize}
  \item \textbf{0}: free, navigable path;
  \item \textbf{1}: wall or rigid obstacle.
\end{itemize}

At this stage of the architectural project, the generation of this clean
matrix by Godot has been isolated as an already-functional ``black box'',
allowing full attention to be devoted to modeling the AI. The initial
binary encoding ($\{0,1\}$) was chosen for its simplicity; additional
channels (agent position, distance to exit, historical traffic density)
can later be concatenated as extra planes of the same matrix without
changing the convolutional extractor's architecture, only the number of
input channels.

\subsection{Convolutional Feature Extractor: Proposed Architecture}
\label{sec:cnn}

The generated 2D matrix acts as the observation (\emph{state}) for the
neural network. To extract the topological patterns of this spatial
environment -- such as narrow corridors, critical routes, and obstacle
density -- the data is proposed to pass through a Deep Convolutional
Network~\cite{lecun1998gradient} (CNN). The nature of CNNs allows the model
to understand the level geometrically, rather than merely reading isolated
numbers, which is essential for recognizing the spatial patterns that
characterize a bottleneck.

Table~\ref{tab:cnn-arch} specifies the proposed feature-extractor
architecture, following the pattern established by grid-world RL work: small
$3\times3$ kernels with stride~$1$, preserving the tile granularity needed
to precisely localize a bottleneck. We deliberately avoid aggressive
max-pooling operations, which would tend to blur exactly the fine
structures (corridors one tile wide) that the system needs to detect.

\begin{table}
  \caption{Proposed convolutional feature extractor $\phi(\cdot)$. Input:
    $G_t \in \{0,1\}^{C \times H \times W}$, with $C=1$ initially.}
  \label{tab:cnn-arch}
  \begin{tabular}{lllll}
    \toprule
    \textbf{Layer} & \textbf{Filters/Units} & \textbf{Kernel} & \textbf{Stride} & \textbf{Act.} \\
    \midrule
    Conv1 & 32  & $3\times3$ & 1 & ReLU \\
    Conv2 & 64  & $3\times3$ & 1 & ReLU \\
    Conv3 & 64  & $3\times3$ & 1 & ReLU \\
    Flatten & -- & -- & -- & -- \\
    FC1 (features) & 256 & -- & -- & ReLU \\
    \bottomrule
  \end{tabular}
\end{table}

The output of FC1 is the latent feature vector $z_t \in \mathbb{R}^{256}$
($d=256$), shared between the policy/value networks and the curiosity
module described below.

\subsection{Policy and Value Networks}
\label{sec:policy-net}

We propose an actor-critic architecture with a shared convolutional trunk
$\phi(\cdot)$ (Table~\ref{tab:cnn-arch}) and two separate heads:
\begin{itemize}
  \item \textbf{Actor head}: a fully connected layer mapping $z_t \in
    \mathbb{R}^{256}$ to $|\mathcal{A}|$ logits, followed by a softmax over
    the discrete action set ($|\mathcal{A}^{\text{nav}}| = 5$ in the
    current navigation-only phase; extended to $|\mathcal{A}^{\text{nav}}|
    + |\mathcal{A}^{\text{edit}}| = 9$ once editing actions are added, per
    Section~\ref{sec:acao});
  \item \textbf{Critic head}: a fully connected layer mapping $z_t$ to a
    single scalar, the state-value estimate $V_\omega(s_t)$, used to
    compute the advantage estimates required by PPO.
\end{itemize}

\subsection{Intrinsic Curiosity Module: Proposed Architecture}
\label{sec:icm-arch}

Following Pathak et~al.~\cite{pathak2017curiosity}, the ICM reuses the
feature encoder $\phi(\cdot)$ and adds two small networks:
\begin{itemize}
  \item \textbf{Inverse model}: takes the concatenation of $z_t$ and
    $z_{t+1}$ ($512$ units), passes it through one fully connected hidden
    layer of $256$ units (ReLU), and predicts the action $a_t$ that
    produced the transition, via a softmax output over
    $\mathcal{A}^{\text{nav}}$. It is trained with a cross-entropy loss
    $L_I$, and its role is to shape $\phi(\cdot)$ so that $z_t$ only
    encodes features relevant to the agent's own actions, ignoring
    aspects of the environment the agent cannot control;
  \item \textbf{Forward model} ($f_\psi$): takes the concatenation of $z_t$
    and a one-hot encoding of $a_t$ ($256 + |\mathcal{A}^{\text{nav}}|$
    units), passes it through one fully connected hidden layer of $256$
    units (ReLU), and predicts $\hat{z}_{t+1}$. It is trained by minimizing
    the mean-squared error between $\hat{z}_{t+1}$ and $z_{t+1}$, which is
    exactly the quantity used as the intrinsic reward in
    Equation~\eqref{eq:reward-int}.
\end{itemize}
The combined ICM training loss follows the standard weighting proposed by
Pathak et~al.:
\begin{equation}
  L_{\text{ICM}} = (1-\lambda)\, L_I + \lambda\, L_F,
  \label{eq:icm-loss}
\end{equation}
with $\lambda = 0.8$ as the literature-informed reference value, giving
more weight to the forward-model loss $L_F$ (which directly produces the
intrinsic reward) while still using the inverse-model loss $L_I$ to keep
the learned features action-relevant.

\subsection{Deep Reinforcement Learning Agent and Proposed Hyperparameters}
\label{sec:drl-hparams}

The agent's decision-making and map exploration rely on a Deep
Reinforcement Learning architecture, combining Curiosity-Driven
Exploration~\cite{pathak2017curiosity} with the foundations of
PCGRL~\cite{khalifa2020pcgrl}. Table~\ref{tab:drl} summarizes the three
central components of the system per the formalization presented in
Section~\ref{sec:formalizacao}.

\begin{table}
  \caption{Components of the Deep Reinforcement Learning system}
  \label{tab:drl}
  \begin{tabular}{p{0.28\linewidth}p{0.6\linewidth}}
    \toprule
    \textbf{Component} & \textbf{Strategy in the project} \\
    \midrule
    Observation (\emph{State}) & The 2D matrix processed by the CNN,
      representing the stage's instantaneous topology ($z_t = \phi(G_t)$). \\
    Action & Discrete vectorial navigation and, later, the ability to flag
      or modify tiles (add/remove blockages). \\
    Reward & Extrinsic/intrinsic combination: strongly penalizes low
      traversal-flow areas (bottlenecks) and rewards exploration of
      regions poorly modeled by the agent. \\
    \bottomrule
  \end{tabular}
\end{table}

Regarding the policy-optimization algorithm, we opt to use \emph{Proximal
Policy Optimization} (PPO)~\cite{schulman2017proximal}, rather than
value-based methods such as Deep Q-Networks. This choice is justified by
three reasons: (i) the action space proposed in Section~\ref{sec:acao} is
naturally discrete, but will be extended to continuous edit-intensity
variations in later phases, and PPO accommodates both cases without a
structural change; (ii) PPO is known for its training stability in
scenarios with sparse and noisy rewards -- exactly the scenario expected
when combining the extrinsic and intrinsic terms of
Equation~\eqref{eq:reward}; and (iii) its on-policy nature simplifies
integration with the curiosity module, which depends on recent
trajectories that are consistent with the current policy so that the
dynamics-model prediction error remains informative.

Table~\ref{tab:ppo-hparams} lists the reference PPO hyperparameter
configuration we propose as a starting point for implementation, following
common defaults reported by Schulman et~al.~\cite{schulman2017proximal} and
widely adopted in standard PPO implementations. These values are
explicitly a proposed initial configuration, to be empirically tuned once
training begins (see Section~\ref{sec:futuro}); they are not the result of
a hyperparameter search.

The wide range proposed for $\beta$ reflects a known open calibration issue
also flagged in Section~\ref{sec:discussao}: the relative scale of the
intrinsic and extrinsic reward terms is environment-dependent and is
expected to require empirical adjustment, rather than being fixed a
priori.

\subsection{Data Integration and Training Pipeline}

Integration between the Godot environment and the training environment
(Python) is planned via a local-socket communication protocol, in which
Godot exports, at every simulation \emph{step}, the serialized matrix $G_t$
and receives back the action $a_t$ chosen by the policy. This process
separation allows training to be accelerated by dedicated hardware (GPU)
without overloading the game engine's rendering and physics loop, and will
later allow multiple environment instances to be parallelized to speed up
trajectory collection, a common practice in deep RL pipelines.

\section{Current Implementation Status}
\label{sec:estado}

With the base communication layer and the AI scope (2D matrix
$\rightarrow$ CNN $\rightarrow$ DRL) validated and defined, the project is
moving toward the formal structuring of the machine-learning components.
As of this writing:
\begin{itemize}
  \item the extraction of the 2D matrix from the \texttt{TileMap} and the
    \texttt{NavigationServer2D} has been implemented and isolated as an
    independent module;
  \item \textbf{preliminary validation performed}: for the handful of test
    levels used during development, the extracted matrix was manually
    inspected and confirmed to match the corresponding \texttt{TileMap}
    layout cell-by-cell; this is a functional/qualitative sanity check of
    the extraction module, not a performance evaluation of the agent, since
    no agent has been trained yet;
  \item the overall design of the CNN~+~DRL pipeline
    (Section~\ref{sec:arquitetura}), including the concrete network
    architecture and the reference PPO hyperparameters, has been defined
    and cross-checked against the PCGRL and curiosity-driven-exploration
    literature;
  \item the formalization of the problem as an MDP
    (Section~\ref{sec:formalizacao}), including the initial hybrid reward
    function proposal, was completed at this stage of the report; and
  \item \textbf{agent training has not yet started}: no PPO run, no
    learning curve, and no bottleneck-detection accuracy number exists at
    the time of writing. The items above constitute the architectural
    groundwork on which the experiments described in
    Section~\ref{sec:avaliacao} will be conducted.
\end{itemize}

\section{Proposed Evaluation Methodology}
\label{sec:avaliacao}

Since agent training is still in the design stage, this section describes
the evaluation methodology planned for the next project cycles, and
\textbf{not} experimental results already obtained. No test run of the
full agent has been performed; the metrics, baselines, and protocol below
define what will be measured once training begins, not what has been
measured so far.

\subsection{Metrics}

We propose the following metrics, with explicit formulas, to evaluate the
agent's ability to identify bottlenecks. Let $\hat{B}$ be the set of cells
flagged by the agent as bottlenecks and $B^\star$ the set of cells
identified as bottlenecks by human experts on a manually annotated
reference-level set. Define true positives $TP = |\hat{B} \cap B^\star|$,
false positives $FP = |\hat{B} \setminus B^\star|$, and false negatives
$FN = |B^\star \setminus \hat{B}|$.

\begin{itemize}
  \item \textbf{Detection precision}:
  \begin{equation}
    \text{Precision} = \frac{TP}{TP + FP}.
    \label{eq:precision}
  \end{equation}

  \item \textbf{Coverage (recall)}:
  \begin{equation}
    \text{Recall} = \frac{TP}{TP + FN}.
    \label{eq:recall}
  \end{equation}

  \item \textbf{$F_1$ score}, summarizing precision and recall in a single
    number:
  \begin{equation}
    F_1 = 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}
      {\text{Precision} + \text{Recall}}.
    \label{eq:f1}
  \end{equation}

  \item \textbf{Visitation-map entropy}: let $p(v) = \text{visits}(v) /
    \sum_{u} \text{visits}(u)$ be the empirical visitation distribution
    over grid cells during an episode. The Shannon entropy
  \begin{equation}
    H = -\sum_{v} p(v) \log p(v)
    \label{eq:entropy}
  \end{equation}
    is used as a proxy to check whether curiosity-guided exploration is
    indeed covering low-flow regions, rather than merely reinforcing
    already well-known routes: a higher $H$ indicates a more spatially
    dispersed visitation pattern.

  \item \textbf{Post-editing bottleneck reduction}: for the future editing-action
    phase (Section~\ref{sec:acao}), the relative change in traversal flow
    $\tau(v)$ before and after the agent's suggested interventions,
  \begin{equation}
    \Delta\tau(v) = \frac{\tau_{\text{after}}(v) - \tau_{\text{before}}(v)}
      {\tau_{\text{before}}(v)},
    \label{eq:delta-tau}
  \end{equation}
    with $\Delta\tau(v) > 0$ indicating that the intervention increased
    traversal flow through a previously identified bottleneck cell.
\end{itemize}

\subsection{Baselines}

As a comparison reference, we plan to include:
\begin{itemize}
  \item a random agent, executing navigation actions uniformly at random,
    to calibrate the performance floor for the metrics above;
  \item a classical \emph{pathfinding} agent (A* search over the navigation
    graph), representing the ``no-learning'' baseline and allowing the
    specific gain attributable to the DRL component to be isolated; and
  \item a variant of the proposed agent itself without the intrinsic
    curiosity term ($\beta = 0$ in Equation~\eqref{eq:reward}), to measure
    the isolated contribution of curiosity-guided exploration relative to
    a purely extrinsic reward.
\end{itemize}

\subsection{Experimental Protocol}

The planned protocol consists of training each agent configuration on a
fixed set of training levels, evaluating periodically on a validation set
of levels not seen during training, in order to verify the policy's
generalization to topologies different from those used in training -- an
essential requirement for the tool to be useful in real level-design
scenarios, where the agent must evaluate novel levels, not only the levels
it was trained on. Each configuration will be run with multiple random
seeds to allow variance analysis across runs, a practice recommended in
the reinforcement-learning literature~\cite{sutton2018reinforcement} given
the well-known sensitivity of these methods to initialization and to the
sampling order of trajectories.

\section{Discussion: Limitations and Risks}
\label{sec:discussao}

Although the proposed architecture is promising, some methodological risks
deserve explicit discussion at this stage of the project.

\textbf{Risk of reward hacking.} Combining extrinsic and intrinsic rewards
(Equation~\eqref{eq:reward}) introduces the classic risk that the agent
exploits artifacts of the reward function itself instead of solving the
intended problem -- for example, lingering in regions whose dynamics model
is intentionally hard to predict (such as areas with chaotic physics),
producing high intrinsic reward without corresponding to an actual design
bottleneck. Mitigating this risk will require careful normalization of the
$r^{\text{int}}_t$ term and, possibly, its decay over the course of
training, as the dynamics model becomes more accurate.

\textbf{Generalization across visual themes and topologies.} Since the
state representation is purely structural (a binary matrix), better
generalization across distinct visual themes is expected than for
pixel-based approaches; however, generalization across topologies that are
structurally very different from those seen in training (for example,
levels with non-orthogonal geometry) has not yet been evaluated and remains
an open risk.

\textbf{Computational cost of distributed training.} The separation
between the Godot process and the training process (Section~\ref{sec:arquitetura})
introduces communication overhead that could become a performance
bottleneck itself -- somewhat ironically, the training pipeline may suffer
from the very type of problem the agent is being trained to detect at the
level of the game. This overhead will need to be measured empirically
before scaling up the number of parallel environments.

\textbf{Validation with human experts.} The precision and recall metrics
proposed in Section~\ref{sec:avaliacao} depend on manual bottleneck
annotation by experts, a process that introduces subjectivity and still
needs to be operationalized -- for example, by defining an annotation
protocol with multiple annotators and inter-annotator agreement measures.

\section{Ethical Considerations and Responsible Use}
\label{sec:etica}

Automated level-design diagnostic tools raise responsible-use questions
that deserve explicit consideration, even at this early stage of the
project.

\textbf{Complementing, not replacing, human judgment.} The proposed system
is meant to provide an additional quantitative signal to the design
process, not to replace human designers' judgment of what makes a level
interesting. A bottleneck flagged by the agent may, in certain intentional
design contexts (for example, a tactical choke point in a competitive map),
be a desired feature rather than a defect to be corrected. The tool should
therefore be used as decision support, with the final call remaining with
the design team.

\textbf{Bias in the definition of fluidity.} The traversal-flow metric
$\tau(v)$ and the centrality weights $w(v)$ (Section~\ref{sec:recompensa})
embed a specific -- and necessarily partial -- definition of what
constitutes a ``fluid'' level. This definition may not be representative of
every play style or player profile (for example, players who prefer slow
exploration over fast progression), and should be communicated
transparently to whoever uses the tool, so that automated recommendations
are not interpreted as objective truths about design quality.

\textbf{Real player data.} At the current project stage, all training
happens in simulation, with no collection of human player data. Should
future stages incorporate real playtesting data -- for example, to
calibrate $\tau(v)$ with telemetry from human matches -- an explicit
consent and anonymization protocol will be required, following standard
practices for research with human participants.

\section{Future Work}
\label{sec:futuro}

With the architecture and problem formalization defined, the project's
next steps include:
\begin{enumerate}
  \item \textbf{Reward function implementation:} implement and
    experimentally calibrate the weights $\beta$, $\eta$, and $\theta_\tau$
    of Equations~\eqref{eq:reward}--\eqref{eq:reward-int}, currently
    defined only at a conceptual level;
  \item \textbf{Editing action space implementation:} extend the
    navigation action space to include the tile flagging and editing
    actions described in Section~\ref{sec:acao};
  \item \textbf{Data integration:} implement the socket-based communication
    protocol between Godot and the training environment described in
    Section~\ref{sec:arquitetura};
  \item \textbf{Reference level set construction:} prepare the manually
    annotated level set required for the precision and recall metrics in
    Section~\ref{sec:avaliacao};
  \item \textbf{Pilot experiments:} train the first versions of the agent
    and of the proposed baselines, enabling a first -- still preliminary --
    empirical validation of the architecture described in this article; and
  \item \textbf{Extension to multiplayer mechanics:} evaluate how the
    traversal flow $\tau(v)$ should be redefined when multiple agents
    occupy the same level simultaneously, competing for the same physical
    space.
\end{enumerate}

\section{Conclusion}
\label{sec:conclusao}

This article reported on the progress and the architecture under
development of a Deep Reinforcement Learning agent for identifying and
correcting level-design bottlenecks in 2D games built on the Godot engine.
Representing the environment as a 2D matrix, processed by a CNN and
consumed by a DRL agent inspired by PCGRL and curiosity-guided exploration,
offers a concrete path beyond traditional pathfinding. We formalized the
problem as a Markov Decision Process, specified a concrete network
architecture (convolutional feature extractor, actor-critic heads, and
Intrinsic Curiosity Module) together with a reference set of PPO
hyperparameters, and outlined an evaluation methodology -- with explicitly
defined metrics, baselines, and an experimental protocol -- for the next
project cycles. We emphasize that, at the time of writing, no training
experiments have been run and no performance results exist; every
architectural and hyperparameter choice presented here is a proposal to be
validated and tuned empirically. We also discussed the most relevant
methodological risks, in particular the risk of reward hacking inherent to
the use of intrinsic rewards. The most immediate future work -- reward
function implementation, editing action space, and data integration --
will build the necessary foundation for the first pilot training
experiments.
